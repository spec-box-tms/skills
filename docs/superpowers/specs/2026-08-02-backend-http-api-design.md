# Backend HTTP API: требования для SpecBox

## Цель

Задать единые правила для backend-требований HTTP API, которые используют
`specbox:extract`, `specbox:propose` и `specbox:review`. Эти правила определяют
размещение и качество спецификаций только при отсутствии соглашений проекта;
они не изменяют формат SpecBoxTMS и не создают новые YAML-поля.

## Размещение и группировка

- Существующие границы feature-файлов сохраняются. Если соглашения нет, один
  YAML-файл описывает ровно одну пару HTTP-метода и шаблона пути.
  Например, `GET /orders/{orderId}` и `PATCH /orders/{orderId}` — разные
  feature-файлы.
- Поле `feature` содержит эту пару метода и пути.
- Поле `code` следует существующему соглашению проекта.
- Существующая группировка `specs-unit` сохраняется. Если её нет, требования
  группируются по HTTP-статусу: `200 OK`, `400 Bad Request`, `403 Forbidden` и
  так далее.
- Несколько причин одного статуса — самостоятельные требования внутри одной
  статусной группы.

## Контракт в `description`

Существующий OpenAPI или принятый в проекте формат контракта сохраняется и не
дублируется. Если такого формата нет, `description` фичи использует Markdown и
содержит блок TypeScript с моделью контракта:

- применимые части запроса: `params`, `query`, `body`;
- модели успешных и ошибочных ответов по статусам.

Модель может использовать тип, описанный другой фичей. Сразу после TypeScript
блока должна быть явная ссылка SpecBox `$<feature-code>` на эту фичу. Ссылки не
размещаются внутри блока кода.

Пример структуры:

````yaml
feature: GET /orders/{orderId}
code: get-order
description: |
  ```ts
  type GetOrderRequest = {
    params: { orderId: string };
  };

  type GetOrderResponse = {
    id: string;
    status: string;
  };

  type ApiError = {
    code: string;
    message: string;
  };
  ```

  Использует модель авторизации $authorization.
specs-unit:
  200 OK:
    - assert: Для существующего заказа API возвращает 200 и модель GetOrderResponse.
  403 Forbidden:
    - assert: Без авторизации endpoint недоступен: API возвращает 403 и модель ApiError $authorization.
  404 Not Found:
    - propose: Для отсутствующего orderId API возвращает 404 и модель ApiError.
````

## Сценарии `assert` и `propose`

Оба вида записей используют один формат текста. Каждая запись описывает один
проверяемый сценарий: входные данные или предусловие, итоговый HTTP-статус,
модель ответа либо существенный побочный эффект. Модель не повторяется
перечнем полей, если она уже задана в `description`.

- `assert` описывает принятое требование. `extract` создаёт его только для
  поведения, подтверждённого реализацией, проходящим behavioral-тестом или
  прямым наблюдением. В delivery-flow `assert` появляется из принятого
  `propose` перед RED-тестом и реализацией.
- `propose` описывает черновик планируемого контракта и не связывается с тестом.

Авторизация описывается отдельной feature. Защищённый endpoint фиксирует
недоступность в своей группе `403 Forbidden` и ссылается на feature
авторизации.

## Общие критерии качества

Reference одинаково проверяет `assert` и `propose`.

Для каждого требования:

- вход или предусловие, статус и результат наблюдаемы;
- формулировка однозначна, реализуема, необходима и проверяема;
- заявленный ответ согласован с моделью в `description`;
- требование находится в группе своего статуса.

Для feature-файла:

- метод и путь определены однозначно;
- статусные группы не противоречат друг другу и модели контракта;
- ссылки на использованные внешние модели существуют.

Для набора backend-файлов:

- пары метода и пути уникальны;
- ссылки разрешаются;
- изменение общей модели остаётся трассируемым через явные ссылки.

## Роли skills

- `specbox:extract` изучает роуты, обработчики, модели и тесты и создаёт только
  подтверждённые `assert`.
- `specbox:propose` создаёт только `propose` по запросу на изменение и не
  меняет код приложения.
- `specbox:review` работает read-only и применяет те же критерии. Для каждого
  замечания он указывает feature, статусную группу, нарушенный критерий и
  минимальное исправление.

## Вне области

- Фоновые задания, очереди и интеграции.
- Новые поля или правила именования YAML-файлов, кроме согласованной единицы
  «метод + путь».
- Изменения CLI, API, хранилища или UI SpecBoxTMS.
