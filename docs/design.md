# Дизайн набора skills SpecBoxTMS

- Статус: утверждён для реализации
- Дата: 2026-08-01

## Контекст

SpecBoxTMS хранит функциональные требования рядом с кодом в YAML-файлах и
сопоставляет их с автотестами. Этот репозиторий добавляет специализированные
Codex skills для полного цикла работы со спецификациями: от подключения
SpecBox к проекту до реализации предложенного изменения.

## Цели

- Разделить работу на семь узких, самостоятельно вызываемых skills.
- Сохранить штатный формат и команды SpecBoxTMS.
- Поддержать черновой `propose` и принятый `assert`; завершение реализации не
  создаёт отдельного ключа YAML.
- Связывать автотесты только с `assert` и не менять статус требования по
  результату теста автоматически.
- Проверять качество требований по критериям Карла Вигерса.
- Разделять frontend- и backend-спецификации без навязывания структуре проекта
  новых соглашений об именах и каталогах.

## Архитектура

Репозиторий будет оформлен как Codex-плагин с именем `specbox`. Пространство
имён добавляется плагином, а имена самих skills остаются допустимыми именами
каталогов без двоеточия.

Планируемая структура:

```text
.codex-plugin/plugin.json
skills/
├── create/SKILL.md
├── extract/SKILL.md
├── validate/SKILL.md
├── write-tests/SKILL.md
├── review/SKILL.md
├── propose/SKILL.md
└── apply/SKILL.md
```

Skills можно вызывать независимо. Для полного цикла `apply` явно использует
`write-tests`; отдельный общий `core` не создаётся. Общие references находятся
в плагине и загружаются только теми skills, которым они нужны. Скрипты и
дополнительные зависимости появляются лишь при наличии повторяемой операции,
которую нельзя надёжно выполнить штатными средствами.

## Доменная модель

### `assert`

`assert` описывает принятое требование. Оно может быть создано для уже
существующего поведения через `extract` или получено из `propose` перед началом
TDD-реализации. Завершённость workflow не кодируется отдельным статусом YAML.

### `propose`

`propose` описывает черновик планируемого поведения. По структуре и правилам
оформления он повторяет `assert`, но не связывается с автотестами.

После принятия `propose` становится `assert`. Затем создаётся RED-тест,
реализуется поведение и подтверждается GREEN-тестом. `completed` означает конец
workflow и не записывается в YAML.

### Покрытие тестами

Покрытие — независимая характеристика требования:

- формат `assert` и `propose` проверяется одинаково;
- с тестовыми отчётами сопоставляются `assert`;
- `propose` не участвует в расчёте покрытия;
- непокрытый `assert`, извлечённый из существующего поведения, не является
  ошибкой валидации;
- детальная картина покрытия остаётся доступной в UI SpecBoxTMS.

### Frontend и backend

Frontend- и backend-требования хранятся в отдельных YAML-файлах. Skill не
фиксирует формат имён файлов, структуру каталогов, суффиксы кодов или новые
поля метаданных.

Перед созданием или выбором файла агент изучает:

- структуру исходного кода;
- существующие спецификации и соглашения проекта;
- тесты и их расположение;
- архитектурные границы затронутого поведения.

Если принадлежность требования к frontend или backend нельзя надёжно вывести
из контекста, агент запрашивает решение пользователя.

## Контракты skills

### `specbox:create`

Подключает SpecBox к новому или существующему проекту. Изучает стек и структуру,
создаёт минимально необходимую конфигурацию `.tms.json` и добавляет
метаинформацию только при реальной потребности. Не создаёт предположительные
требования без источника в задаче, коде или явном решении пользователя.

### `specbox:extract`

Анализирует существующие код и тесты, затем описывает подтверждённое
реализованное поведение как `assert`. Не выдаёт предполагаемое или желаемое
поведение за существующее. Разделяет frontend и backend по контексту проекта и
следует уже принятым соглашениям о размещении файлов.

### `specbox:validate`

Использует штатную валидацию SpecBoxTMS и дополняет её проверками, требуемыми
семантикой `propose`. Проверяет YAML-структуру, обязательные поля, уникальность
кодов, ссылки между фичами и сопоставление `assert` с настроенными тестовыми
отчётами.

Если команда, конфигурация или входные файлы недоступны, возвращает preflight
error и не выдаёт отсутствующие результаты за успешную проверку.

Результат разделяется на:

1. ошибки структуры и ссылок;
2. сведения о сопоставлении тестов;
3. информационный список непокрытых `assert`.

Отсутствие покрытия не меняет код возврата успешной форматной валидации и не
преобразует `assert` обратно в `propose`.

### `specbox:write-tests`

Применяет практики тестирования, подходящие стеку и существующему тестовому
набору проекта. Создаёт или изменяет тесты так, чтобы их идентификаторы
сопоставлялись с `assert` согласно настройкам Jest или JUnit в `.tms.json`.
Для нового `assert` подтверждает RED без изменения кода приложения; для уже
существующего поведения добавляет regression coverage без искусственного
падения. Не навязывает новый тестовый фреймворк.

### `specbox:review`

Выполняет read-only ревью выбранных требований или набора файлов. Для каждого
замечания указывает требование, нарушенный критерий, объяснение и минимальную
рекомендацию. Не редактирует спецификации без отдельного запроса.

### `specbox:propose`

Преобразует запрос на изменение в качественные записи `propose`. Проверяет их
по критериям Вигерса до записи, разделяет frontend и backend по контексту и
сохраняет существующий стиль YAML. Может изменять только явно выбранный набор
затронутых YAML-файлов и не изменяет код приложения.

### `specbox:apply`

Принимает выбранный `propose`, преобразует его в `assert`, через `write-tests`
подтверждает RED, реализует минимальное изменение и подтверждает GREEN.
Результаты этапов и валидации сообщает отдельно; сбой не откатывает принятое
требование автоматически. После GREEN workflow завершается без нового статуса.

## Рабочие процессы

Подключение к существующему приложению:

```text
create → extract → review → validate
```

Изменение поведения:

```text
propose → review → apply: assert → write-tests (RED) → implement → GREEN
                                                            ↓
                                                        completed
```

`write-tests`, `review` и `validate` также могут вызываться независимо.

## Критерии качества требований

`review` и `propose` используют модель Карла Вигерса как базовую, но применяют
её с учётом компактного формата SpecBox.

Для отдельного требования проверяются:

- полнота;
- корректность;
- реализуемость;
- необходимость;
- приоритетность, если проект уже предоставляет способ её выражения;
- однозначность;
- проверяемость.

Для набора требований проверяются:

- полнота;
- непротиворечивость;
- изменяемость;
- трассируемость.

Skill не добавляет в YAML новые поля только ради формального прохождения
критерия. Главная цель — ясная и эффективная коммуникация с разработчиками,
тестировщиками и владельцами продукта.

## Безопасность изменений и обработка ошибок

- Перед записью изучать существующие файлы и сохранять локальные соглашения.
- Не перезаписывать неизвестную конфигурацию и несвязанные изменения
  пользователя.
- Не придумывать поведение, источник которого нельзя установить.
- При неоднозначной границе frontend/backend запрашивать решение пользователя.
- Отделять ошибки формата от замечаний качества и сведений о покрытии.
- Не изменять спецификации во время `review`.
- Не считать отсутствие автотеста доказательством отсутствия поведения.
- Сообщать о неуспешных тестах и валидации без автоматического изменения
  `assert`/`propose` в обратную сторону.

## Реализация skills

Первая версия использует инструкции `SKILL.md`, точечные references и штатные
инструменты проекта: файловые операции, Git, тестовый раннер и
`npx spec-box`. Собственные скрипты не добавляются заранее.

Каждый skill должен:

- иметь точное описание условий срабатывания;
- содержать только свой workflow и необходимые ему знания;
- явно описывать допустимые записи и ожидаемый результат;
- явно объявлять композицию с другим skill, когда она обязательна;
- сохранять решения пользователя и существующие соглашения проекта.

## Проверка skills

Разработка каждого skill выполняется отдельно и завершается до перехода к
следующему:

1. Создать реалистичный сценарий и зафиксировать поведение агента без skill.
2. Написать минимальный `SKILL.md`, устраняющий наблюдённые ошибки.
3. Повторить сценарий со skill и проверить соблюдение контракта.
4. Запустить структурную валидацию skill.
5. Для плагина запустить проверку манифеста и структуры.

Минимальный набор сценариев включает:

- подключение SpecBox к проекту с существующими соглашениями;
- извлечение смешанной frontend/backend-функциональности;
- структурно некорректный YAML и непокрытый `assert`;
- сопоставление теста по настроенным ключам Jest или JUnit;
- неоднозначное или непроверяемое требование;
- предложение, затрагивающее оба слоя приложения;
- полный цикл `propose → assert → RED → implementation → GREEN`.

## Вне области первой версии

- Изменение SpecBoxTMS CLI, API, хранилища или UI.
- Обязательное соглашение об именах и каталогах спецификаций.
- Общий runtime-core или skill-оркестратор.
- Собственный тестовый фреймворк.
- Использование покрытия как блокирующего quality gate.
- Автоматизация UI SpecBoxTMS.

## Критерии готовности набора

- Плагин корректно публикует семь skills с namespace `specbox:`.
- Каждый skill проходит структурную проверку и сценарное тестирование.
- lifecycle `propose → assert → RED → implementation → GREEN` трактуется
  одинаково во всех workflows.
- Непокрытый `assert` не приводит к ошибке форматной валидации.
- Frontend/backend разделяются без навязанной структуры файлов.
- Документация установки создаётся только после появления рабочего каркаса
  плагина.
